# Spec-Driven Development и внедрение OpenSpec в Talking Bob

Дата исследования: **12 сентября 2026**. Срез проекта: `7bc198c`.

**Рекомендация:** использовать OpenSpec со стандартной схемой `spec-driven`,
одной директорией в корне репозитория и постепенным описанием затрагиваемого
поведения. Проект уже располагает контрактами, критериями приёмки и тестами;
основная задача — связать их с единым жизненным циклом изменения.

Цель эксперимента — освоить процесс, который затем пригодится на основной
работе. Рабочая версия, шаблоны и правила пока неизвестны, поэтому план опирается
на базовый OpenSpec. Документ фиксирует исследование и план на момент подготовки.
Актуальная локальная настройка описана в [SDD workflow](sdd-workflow.md);
внедрение конкретных контрактов и CI ведётся отдельными задачами.

## 1. Краткая теория

**Spec-Driven Development (SDD)** — разработка, при которой согласованное
описание поведения задаёт реализацию и критерии её проверки. Спецификацию
сначала уточняют, затем используют при написании кода и поддерживают вместе
с ним. В AI-assisted разработке это даёт агенту устойчивый контекст за пределами
переписки. Такая последовательность лежит в основе
[подхода GitHub к SDD](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/).

Полезно разделять четыре вопроса:

| Артефакт | На какой вопрос отвечает |
| --- | --- |
| Предложение изменения | Какую проблему решаем и где границы задачи? |
| Спецификация | Как система должна вести себя, включая ошибки и ограничения? |
| Технический дизайн | Как реализовать это в текущей архитектуре? |
| Задачи и проверки | Что выполнить и чем подтвердить результат? |

Хорошее требование наблюдаемо: «повторный запрос отдаёт сохранённый отчёт
без нового анализа». Формулировка «улучшить надёжность отчётов» требует уточнения.
Сценарии задают исходное состояние, действие и ожидаемый результат.

SDD совместим с TDD и BDD: спецификация задаёт ожидаемое поведение, тесты
проверяют конкретные случаи, а TDD определяет порядок написания тестов и кода.
Markdown со сценариями сам по себе не становится исполняемым тестом. OpenSpec
проверяет структуру документов; соответствие приложения требованиям требует
тестов и review. [OpenSpec CLI](https://openspec.dev/docs/cli)

Польза для Talking Bob — раньше замечать неоднозначности вроде «повторить
генерацию или доставку», сохранять ограничения между сессиями работы с агентом
и проверять пограничные случаи. Цена — время на согласование и поддержание
документов. Ускорение разработки здесь является гипотезой эксперимента,
а не гарантией инструмента.

Факты о механике взяты из документации разработчиков. Оценка пригодности ниже —

Несколько интеграций, дополнительные проверки согласованности. [Официальный репозиторий](https://github.com/github/spec-kit) | Ближайшая альтернатива для более формализованного процесса. Процесс теснее связан с Kiro; для обучения рабочему OpenSpec это дополнительный инструмент. Kiro уже имеет несколько интерфейсов — утверждение «только IDE» устарело. |
| **BMAD Method** | Более широкий набор ролей и workflows: project context, PRD, architecture, epics/stories; предусмотрены сокращённые маршруты. Начать стоит с одного инструмента. Одновременная установка нескольких систем
создаст разные места для одних требований и затруднит оценку самого OpenSpec.
Сравнение показывает альтернативы, но не даёт оснований менять уже выбранный
пользователем основной инструмент.

## 4. Как разместить OpenSpec и сохранить источники истины

Рекомендуемая структура после первых изменений; это пример, не список папок,
которые нужно создать заранее:

```text
openspec/
  config.yaml
  specs/
    report-delivery/spec.md
  changes/
    <change-name>/
      .openspec.yaml
      proposal.md
      specs/report-delivery/spec.md
      design.md
      tasks.md
    archive/
.agents/skills/openspec-*/
```

Возможные следующие capabilities: `conversation`, `daily-scheduling`,
`streak-reminders`, `admin-analytics`, `admin-broadcasts`. Выделять их следует
по поведению, которое можно проверить; одна capability может затронуть
несколько NestJS-модулей и admin UI.

Для существующего проекта официальная рекомендация — описывать области по мере
работы над ними. Полная предварительная конвертация документации не нужна.
[OpenSpec: Existing Projects](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md)

Предлагаемый порядок владения требованиями:

1. До переноса конкретного поведения нормативными остаются `docs/app.md` и
   `docs/database.md` по существующим правилам репозитория.
2. При переносе ограниченного контракта в OpenSpec одновременно проверить
   его по реализации/тестам и заменить соответствующий нормативный текст
   в старом документе ссылкой. Обновить карту источников в архитектурном индексе
   и инструкции `AGENTS.md`. У одного требования должен быть один владелец.
3. `docs/app.md` постепенно становится обзором и навигацией к перенесённым
   контрактам. Неперенесённые разделы сохраняют свой статус.
4. Prisma schema/SQL migrations сохраняют точное описание хранения;
   `docs/database.md` — пояснения DB-инвариантов и миграций;
   `docs/architecture/` — связи и причины решений;
   `docs/operations.md` — инструкции эксплуатации.
5. Старый backlog хранит историю и приоритеты. Для перенесённой активной задачи
   его статус содержит ссылку на OpenSpec change, а подробные новые задачи
   ведутся в одном `tasks.md`.

Если код расходится с контрактом, сначала зафиксировать расхождение и решить,
что исправлять. Автоматически превращать текущее поведение кода в требование
опасно: так можно закрепить существующий баг.

## 5. План внедрения

### Шаг 1. Подключить инструмент и закрепить версию

В проверенном указателе последнего релиза OpenSpec опубликован **v1.13.0**.
Для воспроизводимого эксперимента предлагается закрепить именно его;
версию для основной работы сверить позднее.
[Release v1.13.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.13.0)

Будущие команды в терминале, в корне Talking Bob:

```bash
node --version
npm install -g @fission-ai/openspec@1.13.0
openspec --version
openspec init --tools codex --profile core
```

OpenSpec требует Node.js не ниже `20.19.0`; версия из `package.json` подходит,
фактическую версию shell следует проверить первой командой. Глобальная CLI
устанавливается отдельно от runtime-зависимостей бота.
[Installation](https://openspec.dev/docs/installation),
[Setup](https://openspec.dev/docs/setup)

`core` включает `explore`, `propose`, `apply`, `update`, `sync`, `archive`.
`verify`, `new`, `continue`, `ff`, `onboard` устанавливаются дополнительно через
`openspec config profile` и `openspec update`. Для начала достаточно `core`;
пошаговый `new/continue` можно попробовать вторым упражнением.
Профиль — настройка машины, а не поле `openspec/config.yaml`.
[Profiles](https://openspec.dev/docs/profiles)

Для Codex актуальная интеграция создаёт skills в `.agents/skills/`;
обращение к ним имеет форму `$openspec-…`. Привычные из примеров
`/opsx:…` — алиасы других инструментов, не команды shell.
[Supported tools](https://openspec.dev/docs/supported-tools)

**Результат шага:** проверить diff после `init`, сохранить существующие skills,
зафиксировать версию и способ повторной настройки в коротком `docs/sdd-workflow.md`.
В Git хранить `openspec/` и проектные generated skills. Правила проекта размещать
в config/AGENTS, чтобы обновление generated skills не затёрло ручные изменения.
Не включать OpenSpec в production Docker image.

### Шаг 2. Задать минимальный контекст проекта

Актуализировать архитектурную справку `AGENTS.md`, добавить ссылки на порядок
владения контрактами и рабочий цикл. В `README.md` дать ссылку на SDD workflow.
Пример будущего `openspec/config.yaml`:

```yaml
schema: spec-driven
context: |
  Talking Bob: Telegram-тренажёр разговорного английского.
  Backend: TypeScript, NestJS, grammy, Prisma/PostgreSQL.
  Admin: Vue/Vite. Сообщения бота и отчёты на русском;
  учебные вопросы и follow-up на английском.
  Сначала читай AGENTS.md и docs/architecture/README.md,
  затем затронутые контракты, код и тесты.
  AI вызывается через интерфейсы и injection tokens;
  Telegram handlers делегируют работу сервисам.
  Сохраняй публичные контракты вне согласованного изменения.
  Язык пояснений — русский; служебный синтаксис OpenSpec сохраняй.
rules:
  proposal:
    - Укажи проблему, границы, non-goals и затронутые контракты.
  specs:
    - Опиши наблюдаемое поведение и проверяемые сценарии ошибок.
  design:
    - Укажи влияние на данные, конкуренцию и совместимость, если оно есть.
  tasks:
    - Свяжи требования с проверками; команды бери из package.json.
    - Включи review, актуализацию контрактов и запись результатов проверок.
```

`context` и `rules` передаются агенту как инструкции; это не программные запреты
и не доказательство их соблюдения. Согласование сложных изменений остаётся
частью действующих правил работы с пользователем.
[Project configuration](https://openspec.dev/docs/project-config),
[config.yaml reference](https://openspec.dev/docs/configuration/config-yaml)

**Результат шага:** агент получает компактный актуальный контекст, а правила
не дублируют целиком большие документы.

### Шаг 3. Провести маленькое учебное упражнение

Для первого знакомства рекомендую **описание существующего контракта повторной
доставки `/report`**. Это ограниченная область с наблюдаемым результатом и уже
существующими проверками. Перенос не должен менять продуктовую семантику.

Материал: раздел Voice conversation and reports в `docs/app.md`,
[ReportHandler](../src/modules/telegram/handlers/report.handler.ts),
[handler tests](../test/report-handler-lifecycle.test.js),
[lifecycle tests](../test/report-lifecycle.test.js),
[journey test](../test/user-journey.test.js).

Последовательность: изучить этот срез → составить проверенную baseline-spec
`report-delivery` → согласовать её → заменить дублирующий поведенческий текст
в `docs/app.md` ссылкой и обновить карту источников истины → проверить ссылки
и соответствие существующим тестам.

Пример **фрагмента baseline-spec**, а не полного контракта:

```markdown
## Purpose

Описывает повторную доставку уже сохранённого отчёта пользователю Telegram,
чтобы запрос результата не приводил к повторному AI-анализу разговора.

## Requirements

### Requirement: Повторная доставка сохранённого отчёта

Система SHALL использовать сохранённый результат анализа при новой команде
/report для последнего вопроса, если отчёт уже успешно сформирован.

#### Scenario: Пользователь повторно запрашивает готовый отчёт
- **GIVEN** для последнего вопроса сохранён сформированный отчёт
- **WHEN** пользователь отправляет новую команду /report
- **THEN** система использует сохранённый анализ для доставки отчёта
- **AND** не вызывает LLM для повторного формирования этого отчёта
```

Для полного выбранного среза также описать definite/ambiguous delivery failure
и различие нового запроса от повторной обработки того же update. Связать сценарии
с уже имеющимися тестами; добавлять тест только при обнаруженном пробеле.
Здесь не нужно придумывать новую функцию ради упражнения.

В следующем **реальном изменении** использовать полный change-цикл из раздела 6.
Кандидат из текущего backlog — один подтверждённый незакрытый сценарий
[исторического покрытия admin-аналитики](backlog/admin-mvp-2026-08/06-admin-analytics-and-charts.md).
Сначала сверить его с кодом: запись `in-progress` не доказывает отсутствие
реализации. Если работа уже завершена, выбрать следующую нужную продуктовую
задачу. Общий [rollout 07](backlog/admin-mvp-2026-08/07-admin-mvp-integration-and-rollout.md)
слишком широк для первого упражнения и зависит от staging evidence.

**Результат шага:** одна небольшая проверенная спецификация и понятная связь
с кодом/тестами; затем один полный цикл настоящего изменения.

### Шаг 4. Подключить проверки к обычной разработке

Команды приложения уже существуют; выбирать их по затронутому поведению:

| Область | Проверка |
| --- | --- |
| Backend и Prisma contract | `npm run test:ci` |
| Сквозной Telegram journey | `npm run test:smoke` |
| Admin UI | `npm run test:admin` |
| DB-инварианты и миграции | `npm run test:postgres` в предусмотренной изолированной среде |
| Контейнеры и эксплуатационный rollout | `npm run test:container` или более широкий `npm run test:operations` по scope |
| Спецификации | `openspec validate --all --strict --no-interactive` |
| Чистота patch | `git diff --check` |

Команды взяты из [package.json](../package.json) и
[CLI reference](https://openspec.dev/docs/cli). Для текущего Admin backlog
сохраняются обязательные проверки его [Definition of Done](backlog/admin-mvp-2026-08/README.md).
Тесты с PostgreSQL/контейнерами требуют подготовленной среды; их пропуск
не равен успешной проверке.

После первого change добавить отдельный CI job для OpenSpec с той же
закреплённой версией CLI. Место автоматизации выяснить при внедрении:
локального workflow сейчас не обнаружено. `validate` проверяет формат,
но не заменяет тесты, смысловой review и проверку результата синхронизации.
Проверять также число найденных спецификаций: пустой bulk validation может
завершиться успешно.

**Результат шага:** спецификации проверяются воспроизводимо; отчёт о проверках
показывает, что выполнено, что не выполнено и почему.

### Шаг 5. Оценить процесс после 3–5 реальных изменений

Для каждого изменения кратко записывать: время на спецификацию, сколько
неоднозначностей нашли до кода, сколько переделок понадобилось из-за требований,
были ли расхождения между spec и реализацией после review.

Критерии полезного эксперимента: требования находятся без истории чата;
у каждого существенного сценария есть проверка; перенос не оставляет
противоречащих нормативных копий; архив отражает реализованное поведение.
Если документы растут быстрее полезной информации — уменьшить scope changes
и детализацию шаблонов. Собственную schema имеет смысл вводить только после
нескольких повторяющихся неудобств стандартного процесса.

## 6. Рабочий цикл одного изменения

```mermaid
flowchart LR
    A[Изучить текущее поведение] --> B[Предложение и сценарии]
    B --> C[Согласовать с владельцем]
    C --> D[Реализация и тесты]
    D --> E[Review по требованиям]
    E --> F[Синхронизация и архив]
    E -->|Требования изменились| B
```

В Codex команды ниже вводятся **в чат**, по одной стадии:

```text
$openspec-explore <область и проблема>
$openspec-propose <change-name и описание>
```

После proposal прочитать требования, границы и технический план. Разрешить
материальные вопросы и явно согласовать сложное изменение перед реализацией.
Затем:

```text
$openspec-apply-change <change-name>
```

Выполнить проверки и review по сценариям. Если изменилось намерение, сначала
обновить согласованные артефакты через `$openspec-update-change`; если код
нарушает принятое требование — исправить код. Дополнительный
`$openspec-verify-change` доступен после включения workflow `verify`.

После готовности выполнить `$openspec-archive-change <change-name>` с
синхронизацией delta specs. Архивирование skill может отдельно запросить sync;
проверить итоговый diff `openspec/specs/`. Основные specs в принятой версии кода
должны описывать реализованное поведение. Незавершённый change остаётся активным.
[Контракты OpenSpec skills](https://openspec.dev/docs/skills)

Изменения спецификаций описываются секциями `ADDED`, `MODIFIED`, `REMOVED`,
`RENAMED Requirements`. `MODIFIED` содержит весь обновлённый блок требования
со сценариями и должен ссылаться на существующее требование. Формат
`### Requirement:` / `#### Scenario:` и слова `SHALL` / `MUST` сохраняются
при русских пояснениях. [Схема spec-driven](https://openspec.dev/docs/schemas/spec-driven)

Практические правила для проекта:

- Один change — один ограниченный результат. В PR связать proposal, код,
  проверки и обновлённые контракты; применять English Conventional Commits.
- Для исправления поведения сценарий показывает условие воспроизведения
  и ожидаемый результат. Уже выполненные задачи не создавать заново.
- Для опечаток и правок без изменения поведения использовать обычный небольшой
  patch. Если такой работе нужен OpenSpec tracking, текущая схема позволяет
  явно указать `skip_specs: true` в `.openspec.yaml`; выдумывать требования
  ради валидатора не нужно. [Правила schema](https://openspec.dev/docs/schemas/spec-driven)
- Перед завершением проверить все затронутые acceptance criteria, включая
  error/retry/empty/disabled states, когда они применимы. Галочка в `tasks.md`
  требует свидетельства выполнения.
- Production rollout не считается подтверждённым локальными тестами.
  Существующее требование staging evidence для Admin task 07 сохраняется.

## 7. Что уточнить перед фактическим внедрением

Исследование не блокируется вопросами. Перед установкой достаточно согласовать
шаги 1–3 и область baseline; перед первым продуктовым change — выбрать конкретную
нужную задачу. При появлении информации с основной работы сверить версию,
schema, язык артефактов, AI-инструмент и обязательные проверки. Базовые навыки —
формулирование требований, проверка сценариев, работа с дельтами и review —
останутся применимыми при другой конфигурации.

# OpenSpec: как мы с ним работаем

Памятка для Talking Bob. Наша настройка: OpenSpec 1.13.0, Codex, схема `spec-driven`.

OpenSpec помогает сначала договориться, **как должна работать функция**, а затем
написать код и проверить результат. Договорённости сохраняются в файлах проекта,
поэтому их можно прочитать, исправить и использовать в следующем чате.

Ты описываешь задачу и принимаешь решения. Codex изучает проект, пишет документы,
реализует и проверяет код. OpenSpec CLI даёт структуру, шаблоны и команды для
ведения изменения. Содержание документов агент составляет по твоему запросу,
существующим требованиям, коду и тестам.

## Что означают папки и файлы

**Spec** — описание ожидаемого поведения. **Capability** — область этого поведения,
например доставка отчёта (`report-delivery`). **Change** — одна законченная задача;
она может затрагивать несколько областей.

Ниже структура с примером будущего активного изменения `<change-name>`:

```text
AGENTS.md                              общие правила работы агента
.agents/skills/openspec-*/              инструкции агенту для этапов OpenSpec
openspec/
├── config.yaml                        настройки и краткий контекст проекта
├── specs/
│   └── report-delivery/spec.md         актуальные требования к доставке отчёта
└── changes/
    ├── <change-name>/                  рабочая папка одной задачи
    │   ├── .openspec.yaml              служебные настройки изменения
    │   ├── proposal.md                 зачем делаем и что входит в задачу
    │   ├── specs/<capability>/spec.md   какие требования меняем
    │   ├── design.md                   как реализуем, если нужны пояснения
    │   └── tasks.md                    шаги реализации и проверки с галочками
    └── archive/                       история завершённых изменений
```

**Два каталога `specs` нужны для разных моментов времени.** В корневом
`openspec/specs/` мы поддерживаем согласованное реализованное поведение.
Внутри change лежит *дельта*: что предлагаем добавить, изменить или убрать.
После реализации переносим эти изменения в основные specs и архивируем change.

Набор документов задаёт выбранная схема `spec-driven`. Создавать всё вручную
не требуется: агент использует CLI и заполняет нужные документы. `design.md`
нужен для технических решений; в нашем простом переносе документации мы его
осознанно пропустили. См. [цикл OpenSpec](https://openspec.dev/docs/quickstart).

## Как проходит одна задача

1. **Описываешь проблему.** Что нужно пользователю, что происходит сейчас и чего
   ожидаешь. Если решение ещё неясно, сначала просишь исследовать варианты.
2. **Просишь подготовить изменение.** Агент создаёт предложение, требования,
   при необходимости дизайн и список задач. Реализация идёт следующим этапом.
3. **Проверяешь смысл.** В первую очередь читаешь `proposal.md` и сценарии в
   `specs/`: правильно ли понята задача, учтены ли ограничения и ошибки.
   Пишешь правки обычными словами. Когда всё устраивает, даёшь аппрув реализации.
4. **Агент выполняет задачи.** Меняет код, запускает подходящие проверки,
   делает review и отмечает подтверждённый результат в `tasks.md`. Если меняется
   само требование, сначала согласуем и обновляем документы.
5. **Принимаем результат и закрываем изменение.** Сверяем код с требованиями,
   синхронизируем основные specs, переносим change в архив. Незавершённые проверки
   остаются явно отмеченными и мешают считать задачу готовой.

Для нашей установленной интеграции можно писать в **чат Codex**:

| Что нужно | Пример обращения |
| --- | --- |
| Подготовить задачу | `$openspec-propose <название и описание задачи>` |
| Начать после review | `План принимаю. $openspec-apply-change <название>` |
| Завершить | `Результат принимаю. $openspec-archive-change <название>` |

Названия запоминать необязательно: «Подготовь OpenSpec-изменение для …» тоже
подходит. Можно править документы самому или попросить агента. CLI проверяет
структуру; соответствие поведения требованиям подтверждаем тестами и review.

На GitHub-доске показываем крупную задачу, а детали оставляем в `tasks.md`.
Публичные действия требуют аппрува; движение карточки подтверждённо приватной
доски в рамках задачи — нет. Архивирование OpenSpec само по себе ничего
не публикует. Правила и команды подробнее — в [рабочем процессе](sdd-workflow.md).

## Пример, который у нас уже есть

В [спецификации доставки отчёта](../openspec/specs/report-delivery/spec.md)
зафиксировано: когда готовый отчёт сохранён и доступен, новая команда `/report`
использует этот результат без повторного LLM-анализа.

**Требование** описывает правило, а **сценарий** — проверяемый пример:
«Когда пользователь снова запрашивает готовый отчёт, тогда используем сохранённый
результат и не запускаем повторный анализ». В файле этому соответствуют
`Requirement`, `Scenario`, `WHEN` и `THEN`; `SHALL` означает «система должна».

Мы описали уже существующее поведение, сверили его с кодом и тестами и сохранили
[историю изменения](../openspec/changes/archive/2026-09-12-document-report-delivery-baseline/proposal.md).
Там же лежат `verification.md` с результатами проверок и `documentation.patch`:
это наши дополнительные материалы, а не обязательные файлы каждого change.

## Почему файлы не заполняют весь контекст — и когда могут

**Контекст модели — ограниченный объём текста, доступный ей при ответе:**
инструкции, история общения и прочитанные через инструменты материалы.
Наличие файла на диске само по себе не означает, что весь его текст уже там.

| Материал | Как попадает в контекст |
| --- | --- |
| Применимые `AGENTS.md` | Codex собирает инструкции при старте. Поэтому общие правила тоже занимают место. [Документация Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md) |
| Skills OpenSpec | Сначала доступны краткие сведения о skills; полный `SKILL.md` читается при использовании выбранного skill. [Загрузка skills](https://learn.chatgpt.com/docs/build-skills) |
| `config.yaml` | OpenSpec добавляет поле `context` в инструкции для каждого документа изменения, а `rules` — для соответствующего типа документа. [Настройки OpenSpec](https://openspec.dev/docs/configuration/config-yaml) |
| Specs, changes, код, архив | Их содержимое попадает в контекст, когда агент читает его или оно явно передано в чат. Само дерево папок не загружает все файлы. |

Поэтому при работе над доставкой отчёта агенту обычно достаточно текущего change,
связанных требований, участков кода и тестов. История всех старых задач для этого
не нужна. В наших настройках также есть несколько общих документов для начала работы.

**OpenSpec не гарантирует экономию контекста.** Если читать всё подряд, повторять
большие документы или вести очень длинный чат, объём растёт. Перенос в `archive/`
не удаляет уже прочитанный текст из разговора. Сокращение истории самим агентом —
отдельный механизм, а не действие OpenSpec.

Практика для нас: вести один change за раз, держать общие инструкции короткими,
читать только нужные области и не дублировать требования в нескольких местах.
После долгого обсуждения можно начать новый чат: «Продолжи изменение `<название>`:
прочитай его документы, проверь состояние задач и кода». Файлы позволяют
восстановить договорённости без переноса всей переписки; сами они должны оставаться
актуальными.

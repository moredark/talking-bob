# План развертывания Talking Bob на одном Linux-сервере

## 1. Зафиксировать production-архитектуру

- [ ] Развернуть четыре компонента в Docker Compose: `postgres`, одно приложение `app`, статическую сборку `admin` и reverse proxy.
- [ ] Оставить ровно один экземпляр `app`, пока Telegram long polling и планировщик не получат распределенную блокировку.
- [ ] Открыть наружу только reverse proxy на портах `80` и `443`; не публиковать порты PostgreSQL и NestJS.
- [ ] Обслуживать admin и API с одного origin: admin всегда обращается к `/api`, а reverse proxy направляет `/api/*` к существующим маршрутам NestJS со снятием префикса `/api`.
- [ ] Настроить общий SPA fallback на `index.html` для всех клиентских маршрутов, включая прямое открытие `/`, `/login`, `/users`, `/users/:id`, `/prompts`, `/topics` и `/error-logs`.
- [ ] Завершать TLS на reverse proxy и перенаправлять HTTP на HTTPS.

## 2. Подготовить production-файлы проекта

- [ ] Перевести backend Dockerfile на многостадийную сборку с `npm ci`, `prisma generate`, `npm run build`, минимальным runtime-слоем и непривилегированным пользователем.
- [ ] Добавить воспроизводимую сборку admin через `cd admin && npm ci && npm run build`.
- [ ] Добавить конфигурацию reverse proxy для статики, SPA fallback, `/api/*`, TLS и корректных proxy headers.
- [ ] Подготовить production Compose-конфигурацию с внутренней сетью, постоянным томом PostgreSQL, restart policy, ограничениями ресурсов и фиксированными версиями образов.
- [ ] Добавить легковесный health endpoint backend и healthchecks для PostgreSQL, backend и reverse proxy.
- [ ] Настроить ожидание готовности PostgreSQL перед миграциями и запуском backend.
- [ ] Сохранить существующие публичные маршруты и контракты backend/admin без переименования.

## 3. Оформить контракт переменных окружения

- [ ] Хранить реальные production-значения только в серверном `.env`, исключенном из Git, с владельцем deploy-пользователем и правами `600`.
- [ ] Оставить `.env.example` шаблоном без секретов и синхронизировать его с фактическими потребителями.
- [ ] Задать обязательные runtime/Compose-переменные: `DATABASE_URL`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `TELEGRAM_BOT_TOKEN`, `CLOUD_RU_API_KEY`, `JWT_SECRET`, `ADMIN_CORS_ORIGIN`.
- [ ] Для `JWT_SECRET` использовать криптографически случайное значение и не допускать production-запуск с fallback-секретом.
- [ ] Задать `ADMIN_CORS_ORIGIN` равным итоговому HTTPS-origin админки.
- [ ] Описать опциональные runtime-переменные и их значения по умолчанию: `LLM_API_URL`, `LLM_MODEL`, `LLM_ANALYSIS_MAX_TOKENS`, `LLM_FOLLOWUP_MAX_TOKENS`, `PORT`.
- [ ] Использовать `ADMIN_USERNAME` и `ADMIN_PASSWORD` только во время первоначального seed администратора и не передавать их постоянно работающему приложению.
- [ ] Дополнить шаблон опциональным ключом `LLM_API_URL`, если на сервере требуется переопределить встроенное значение.
- [ ] Перед стартом проверять наличие всех обязательных значений без вывода секретов в логи.

## 4. Подготовить сервер

- [ ] Выбрать поддерживаемый Linux-дистрибутив, создать непривилегированного deploy-пользователя и ограничить SSH-доступ ключами.
- [ ] Установить Docker Engine и Docker Compose plugin из официального репозитория.
- [ ] Настроить синхронизацию времени, автоматические security-обновления и ротацию системных/Docker-логов.
- [ ] Направить DNS-записи домена на сервер.
- [ ] Открыть в firewall только SSH, `80/tcp` и `443/tcp`; закрыть `3000`, `3001` и `5432`.
- [ ] Создать каталог релизов, каталог резервных копий и постоянный том PostgreSQL с ограниченным доступом.

## 5. Подготовить базу данных и первоначальные данные

- [ ] Оставить PostgreSQL доступным только по внутренней Compose-сети и добавить `pg_isready` healthcheck.
- [ ] Перед первой миграцией проверить подключение по production `DATABASE_URL`.
- [ ] Создать резервную копию перед каждым обновлением схемы.
- [ ] Выполнять `npm run deploy:init` отдельным one-shot Compose-сервисом до запуска приложения: дождаться PostgreSQL, применить `prisma migrate deploy`, затем запустить идемпотентные seeds.
- [ ] Автоматически добавлять только отсутствующие встроенные prompts; разрешить prompts без `audioFileId` и отправлять их текстом.
- [ ] Создавать администратора только при одновременно заданных `ADMIN_USERNAME` и `ADMIN_PASSWORD`; после первоначального создания разрешить убрать их из окружения следующих релизов.
- [ ] Проверять повторный запуск init на тестовой базе: число встроенных prompts не должно увеличиваться.

## 6. Выполнить первый релиз

- [ ] Зафиксировать релиз Git-тегом или commit SHA и использовать неизменяемые теги Docker-образов.
- [ ] До отправки на сервер выполнить:
  - [ ] `npm ci`
  - [ ] `npm run build`
  - [ ] `cd admin && npm ci`
  - [ ] `cd admin && npm run build`
- [ ] На сервере создать production `.env`, проверить права доступа и выполнить `docker compose config` без публикации результата с секретами.
- [ ] Собрать или получить образы выбранного релиза.
- [ ] Запустить PostgreSQL и дождаться статуса `healthy`.
- [ ] Запустить Compose stack: `init` должен завершить миграции и seeds, после чего `app` запускается только командой `node dist/main.js`.
- [ ] Перед каждым init сделать backup базы данных.
- [ ] Запустить `app` в одном экземпляре, затем reverse proxy/admin.
- [ ] Получить и проверить TLS-сертификат, автоматическое продление и редирект с HTTP на HTTPS.
- [ ] Проверить `docker compose ps` и логи каждого сервиса перед открытием доступа пользователям.

## 7. Проверить развертывание

- [ ] Проверить healthchecks и отсутствие циклических перезапусков контейнеров.
- [ ] Перезапустить `app` без выполнения миграций и убедиться, что он запускается командой `node dist/main.js`.
- [ ] Повторно запустить `init` и убедиться, что built-in prompts и admin не дублируются.
- [ ] Проверить прямое открытие SPA-маршрутов `/`, `/login`, `/users`, `/users/:id`, `/prompts`, `/topics` и `/error-logs`; исключить ответы `404` от reverse proxy.
- [ ] Проверить, что браузер обращается к same-origin `/api`, а proxy корректно передает запросы к `/auth/*` и `/admin/*`.
- [ ] Проверить вход администратора, чтение dashboard/users/prompts/error logs и одну безопасную операцию записи.
- [ ] Проверить запуск Telegram long polling, команды `/start`, `/settings` и `/report`.
- [ ] Проверить полный voice-flow: скачивание сообщения, распознавание Cloud.ru, LLM-анализ и текстовый ответ бота.
- [ ] Проверить одно срабатывание расписания и отсутствие дублирующих отправок.
- [ ] Проверить, что PostgreSQL и backend недоступны напрямую из интернета.
- [ ] Проверить логи на отсутствие секретов, connection errors и необработанных исключений.

## 8. Настроить эксплуатацию, обновления и откат

- [ ] Настроить регулярный `pg_dump` или согласованные snapshot-копии, шифрование, срок хранения и копирование за пределы сервера.
- [ ] Провести тестовое восстановление backup в отдельную базу и записать проверенную команду restore.
- [ ] Настроить мониторинг доступности HTTPS, health endpoint, свободного места, состояния контейнеров и свежести backup.
- [ ] Зафиксировать процедуру обновления: backup → получение нового immutable image → миграции → запуск → smoke-check.
- [ ] Хранить предыдущий рабочий тег образа и Compose-конфигурацию для быстрого отката приложения.
- [ ] Перед миграцией определить ее обратную совместимость; при несовместимой схеме выполнять откат только вместе с восстановлением базы из backup.
- [ ] Не масштабировать backend более чем до одного экземпляра без распределенной блокировки планировщика и безопасной стратегии Telegram updates.

## Context

Мотивация и границы — в [proposal.md](proposal.md). `VoiceHandler` сейчас совмещает аудиоадаптер и оркестрацию turn; `ConversationService` владеет транзакционным приёмом, `ReportWorkflowService` — анализом и доставкой. `ReportHandler` уже читает user-реплики независимо от наличия voice id. `SpokenReplyService` определяет исходящий формат, а `ScheduleHandler.handleTimeText` потребляет весь непустой обычный текст в активном окне ввода времени, включая невалидное время.

`ConversationMessage` и `UserResponse` допускают null в `voiceFileId`. Внутренний `AcceptVoiceData.voiceFileId` пока обязателен. `UserResponse.transcript` уже формируется объединением всех user content. `noVoiceForDays` в `broadcast-snapshot.ts` и pre-send eligibility опирается на `lastUserMessageAt`; это корректно для нынешнего единственного голосового входа, но требует разделения после добавления текста. Существующий сценарий Contradictory selections в `schedule-reengagement` поэтому явно пересматривается дельтой.

## Goals / Non-Goals

**Goals:** одна application-операция продолжения разговора для обоих транспортных входов; сохранение владельцев состояния, квот, lock order, fencing и интерфейсов AI; отсутствие аудио-I/O на текстовом пути; совместимое различение общей и голосовой активности.

**Non-Goals:** новые Nest-модули, очереди, библиотеки, форматы анализа, поля с копией текста, изменение правил TTS и модели письменной оценки. Отдельный persistent enum формата сообщения не нужен: для сохранённой user-реплики наличие voice id уже различает источник, а retention удаляет сами сообщения.

## Decisions

### Общая оркестрация внутри TelegramModule

Выделить существующий post-transcription сценарий в `PracticeReplyWorkflowService` внутри Telegram-модуля. `VoiceHandler` сохраняет проверку duration/size и ограниченную загрузку/Whisper; новый `TextHandler` проверяет текст. Оба используют общий preflight (пользователь, последний sent prompt, duplicate/closed, admission) и передают нормализованное содержание в общий workflow. Это application-сервис в существующих границах модулей, аналогично `ReportWorkflowService`, без зависимостей handler-to-handler. Не копировать readiness, follow-up, typing lifecycle, personality resolution и обработку ошибок в два handler.

Отдельные независимые реализации проще только в первой правке, но создают риск разного закрытия диалога. Передача искусственного voice payload из текста в `VoiceHandler` сохраняла бы ложную связь с аудио. Общий workflow позволяет оставить адаптеры тонкими и вызывать провайдеры через прежние injection tokens.

### Маршрутизация и ограничения

Порядок: команды → существующий `handleTimeText` → `message:text` для практики. Дополнительно исключать любой текст после trim с начальным `/`, включая неизвестную команду, из практики. Сохранить текущую отмену time input командами/внешними callbacks. Обработчик текста получает только новые `message:text`, без `edited_message` и caption. Handler promise возвращается целиком в runner, сохраняя same-chat FIFO и shutdown drain.

Trim удаляет только крайние пробелы; максимум 4096 UTF-16 units — фиксированное ограничение MVP, без новой настройки. Сохраняются внутренние переносы, emoji и символы разметки. Проверка до квоты/AI ограничивает стоимость некорректного ввода. Существующие ограничения AI payload, в том числе 1800 символов sample, сохраняются: лимит входа не обещает анализ каждого символа длинного ответа.

### Единая квота и транзакционный приём

Оставить action `voice_response` и `VOICE_RESPONSE_MAX_REQUESTS`/`VOICE_RESPONSE_WINDOW_MINUTES` как совместимые внутренние имена общей квоты. Отдельный text quota дал бы удвоенный allowance. Учитывать прежние записи в `UserRequest`; поведение квоты после допущенной, но неудачной обработки сохраняется. Обновить пользовательские тексты лимита, welcome и no_messages на общий ввод.

Обобщить voice-named типы и методы `ConversationService` в приём user-реплики с необязательным voice id, обновив внутренние вызовы/тесты. Текстовая запись содержит `voiceFileId = null`. Сохранить prompt row lock, dedupe `telegramUpdateId`, проверку snapshot перед acceptance, guarded assistant insert, один generation owner и атомарную квалификацию дня. Readiness использует общую историю и тот же минимальный порог meaningful English. При исчерпании readiness retries сначала принять ответ с `ready=false`, затем сообщить о сохранении и предложить `/report`, как на нынешнем голосовом пути.

Автоматический и ручной отчёты должны выбирать один и тот же первый ненулевой voice id в порядке истории, а при исключительно текстовом разговоре сохранять null. Содержимое `transcript` остаётся общей последовательностью user content; имя поля и публичный analysis version не меняются. Отдельное различение ASR и набранного текста в LLM не требуется: согласованно сохраняется прежняя оценка английского без орфографии/пунктуации.

Пустая история после retention не означает отсутствие отчёта: при нулевом числе
реплик `claimGeneration` проверяет сохранённого generated owner под блокировкой
и возвращает его lifecycle, чтобы handler сообщил об истечении срока хранения.
Повторный анализ и создание delivery для очищенного содержимого не запускаются.

### Общая активность и последнее голосовое время

Добавить `User.lastVoiceMessageAt DateTime? @db.Timestamptz(3)` как несекретный факт, аналогичный `lastUserMessageAt`. В транзакции принятия любого ответа обновлять общую активность, `firstUserMessageAt`, `UserActivityDay`; только при наличии voice id обновлять `lastVoiceMessageAt`, монотонно по времени принятия. Duplicate/rollback не меняют ни один факт. Существующий reset progress очищает оба времени в одной транзакции.

Сохранить `noVoiceForDays` и его публичную подпись: перенести predicate snapshot и pre-send recheck на `lastVoiceMessageAt`. Общие activity-фильтры сохраняют `lastUserMessageAt` и теперь естественно учитывают текст. Это требует дельты двух требований `schedule-reengagement`, поскольку «активен текстом, но не отвечает голосом» становится реальным сочетанием.

Выборка последнего голоса из `ConversationMessage` без нового поля не подходит: retention удаляет историю и меняет eligibility задним числом. Переименование фильтра в «нет ответов» меняло бы согласованный пользовательский контракт и существующие кампании. Новая колонка сохраняет семантику без изменения API и без хранения чувствительного содержимого.

## Risks / Trade-offs

- Общий workflow затрагивает рабочий голосовой путь → сначала перенести сценарий с сохранением поведения и проверить voice/runtime tests, затем подключить текст.
- Длинный допустимый ответ сохраняется целиком, но AI sample остаётся ограниченным → сохранить текущие bounds и не обещать новый вид полного письменного анализа.
- Текст в активном time input воспринимается как попытка времени → сохранить явно описанный приоритет и проверить ошибку формата, истечение и отмену через настоящую middleware chain.
- Голосовой timestamp требует корректного backfill → выполнить миграцию и финальную сверку до включения текстового ввода; не восстанавливать его из уже очищенной истории.
- Legacy имена квоты и `analyzeSpeech` шире фактического смысла → сохранить их совместимость; пользовательские подсказки используют общий термин «ответ».
- Сбой follow-up после сохранения turn не имеет durable retry → сохранить действующую семантику и `/report` recovery; не вводить автоматическую повторную отправку.

## Migration Plan

1. Новая additive migration создаёт nullable `lastVoiceMessageAt` и заполняет его из `lastUserMessageAt`: до текстового ввода все accepted user turns голосовые, включая сохранённые retention-safe факты. Значение null сохраняется для никогда не отвечавших. Новые библиотеки и изменения схемы сообщений не нужны.
2. Для текущего deploy с заменой процесса остановить приём updates/фоновые broadcast workers, дождаться drain, применить миграцию и финально сверить голосовое время с общим до старта новой версии. Это исключает окно, где старый процесс принял голос после backfill. Для будущего rolling deploy потребуется отдельный expand/dual-write этап; он не входит в текущую схему запуска.
3. Новая версия одновременно включает dual activity write, voice-specific broadcast predicates и текстовый маршрут. Проверить старых пользователей, исключительно текстовый отчёт с null voice id, смешанную историю, reset progress и сохранённые кампании без новых полей API.
4. Retention удаляет текст и анализ существующим механизмом; оба несекретных activity timestamps остаются. Логи используют stage/request/correlation metadata без содержимого. Для отдельной операции `text.process` согласовать sanitization/allowlist административных error logs.
5. При откате сохранить additive колонку и данные. Точный возврат старого бинарника после текстовой активности нарушит голосовую семантику `noVoiceForDays`, поскольку он читает общий timestamp: нужен rollback build с отключённым текстовым маршрутом, но сохранёнными voice-specific predicate и dual writes. Не удалять текстовые данные и не переписывать общую активность ради rollback.

При реализации обновить затронутые абзацы `docs/app.md` ссылкой на `text-practice-replies`, сохранив описание голосовых bounds/TTS и остальные контракты; обновить `docs/database.md`, архитектурные страницы и индекс источников. Sync реализованных дельт выполняется штатным OpenSpec workflow.

## Usage metrics extension

По дополнительному запросу пользователя метрики входят в текущий change.
`UserActivityDay` получает `textMessageCount` и `voiceMessageCount` (default 0),
которые увеличиваются вместе с общим `messageCount` в существующем atomic upsert.
CHECK: оба неотрицательны, сумма не больше общего числа; остаток — неизвестное
историческое распределение. Дубли, ранние отказы и rollback не добавляют событий.
Reset удаляет строки существующим способом, retention сохраняет агрегаты.

Отдельная additive migration `20261116130000_reply_usage_metrics` добавляет поля
и `AdminAnalyticsCoverage.replyUsageCompleteFrom` с timestamp начала учёта.
Исторические counters остаются 0: после purge точный формат неизвестен. При
внедрении новые counters включаются одновременно с приложением после drain;
старая версия после миграции сдвигает фактическое начало полного покрытия, так
что rolling deploy не используется. Новые библиотеки/таблицы не нужны.

`GET /admin/analytics` сохраняет version 1 и получает additive `replyUsage`:
coverage со своим completeFrom/status; users (total, text, voice, mixed,
textSharePct); replies (total, text, voice); daily rows с теми же users/counts.
Период — существующие 7/30/90 московских календарных дней. Пользователь текста
считается один раз за период при хотя бы одной принятой текстовой реплике;
mixed означает оба формата в периоде, в том числе в разные дни. Доля текста —
text users / total users с известным форматом; при пустом знаменателе null.
Общие activity-фильтры и прежняя аналитика не переопределяются.

Один дополнительный SQL query в RepeatableRead читает только durable дневные
агрегаты: группировка по пользователю для summary и по дате для daily. Дневные
уникальные пользователи не суммируются для вычисления уникальных за период.
Нулевые дни заполняются в API; отдельное coverage не позволяет принять старые
неизвестные данные за полную историю. Содержимое сообщений не читается.

Dashboard использует существующие AnalyticsSection, StatsCard, MetricBarChart
и AccessibleDataTable с прежним переключателем периода. Показываются summary,
начало учёта/частичное покрытие и дневные значения. Пользователь, применявший
оба формата, входит в обе format-specific группы; пояснение делает это явным.

## Context

Мотивация и согласованный продуктовый scope — в [proposal.md](proposal.md). Изменение затрагивает Telegram, календарные вычисления, хранение расписания и административную рассылку, поэтому нужен отдельный design.

Наблюдаемые опоры в коде:

| Область | Текущая точка расширения |
| --- | --- |
| Telegram | `handlers/settings.handler.ts` содержит `TIME_OPTIONS`, переключатели и валидируемые `set_time_H_M`; `telegram.service.ts` регистрирует handlers и меню команд |
| Расписание | `ScheduleService` — фасад; `schedule-settings.operations.ts` обновляет настройки под User lock; `schedule-claims.operations.ts` резервирует due-occurrence и продвигает `nextPromptAt` одной транзакцией |
| Время | `shared/time/timezone.ts`: `nextSlotAtOrAfter`, `nextSlotStrictlyAfter`, `latestSlotAtOrBefore` рассчитаны на ежедневный слот; `resolveWallClock` уже задаёт DST-политику |
| Активность | `ConversationService.acceptVoiceAndMaybeClaimGeneration` монотонно обновляет `User.lastUserMessageAt` при принятии реплики в той же транзакции; retention сохраняет этот факт |
| Рассылка | `AdminBroadcastsService.preview/create`, `broadcast-audience.ts` (Prisma predicate), `broadcast-snapshot.ts` (INSERT SELECT), `BroadcastDispatcher` (lease, attempt marker, retry) |
| Admin UI | `BroadcastCreatePage.vue` уже имеет signature preview, пустое/ошибочное состояние, подтверждение и блокировку действий при запросе; страницы списка/деталей и `admin/src/types/index.ts` обслуживают тот же API |
| Стрик | `StreakService.updateReminderEnabled` уже выполняет пересчёт/отмену; квалификация и snapshots отчёта отделены от расписания вопросов |

Пять broadcast routes и внешние методы фасада расписания сохраняются. Нормативные документы до реализации: `docs/app.md`, `docs/database.md`, `prisma/schema.prisma`; `report-delivery` не затрагивается.

## Goals / Non-Goals

**Goals:**

- Сохранить PostgreSQL как единственный durable owner расписания и рассылки; расширить существующие операции без новой очереди или фонового сервиса.
- Описать независимые фильтры одним набором правил для preview, snapshot и применимой проверки перед отправкой, с тестами эквивалентности Prisma и SQL вариантов.
- Дать короткий, адресный режим ввода времени в личном чате, не связывая его с conversation state, БД или обработкой голосовых сообщений.

**Non-Goals:**

- Новая универсальная система Telegram wizard-сессий, произвольных кнопок в рассылках или шаблонизации персональных сообщений.
- Изменение `StreakDay`, модели отчётов, правил readiness или алгоритма квалификации.
- Обновление UI-библиотек, регистрация новых провайдеров или расширение редактирования профиля пользователя в админке.

## Decisions

### 1. Хранить дни как компактную маску рядом с существующим временем

Добавить `User.promptWeekdaysMask Int @default(127)` и SQL CHECK `1 <= promptWeekdaysMask AND promptWeekdaysMask <= 127`. Биты 0–6 означают ISO-дни 1–7 (понедельник–воскресенье); 127 — все дни. `dailyPromptEnabled` сохраняет имя и отвечает за автоматические вопросы любой частоты. Ручной режим — `false`, с сохранённой непустой маской и временем; пустая маска не кодирует выключение. В UI термин «Ежедневные вопросы» в затронутых фильтрах заменить на «Вопросы по расписанию».

В `ScheduleSettings` добавить optional mask. При чтении/записи использовать текущую маску, если её нет в patch; `initializeSchedule`, `enableSchedule`, `disableSchedule` не сбрасывают дни. Новые User create/upsert получают 127. Не менять сигнатуры публичных методов, существующие hour/minute/timezone и occurrence metadata.

Альтернативы: массив ISO-дней требует дополнительных checks на дубликаты/диапазон; отдельная таблица нужна для времени на каждый день, чего нет в scope. Маска достаточна для одного повторяющегося недельного слота и не добавляет библиотек.

### 2. Добавить weekday-aware вычисления без изменения календаря стриков

Добавить отдельные weekday-aware helpers в `shared/time`, переиспользующие `resolveWallClock` и локальную календарную арифметику. Старые daily helpers оставить совместимыми для стриков и других клиентов. Внешнее представление `ScheduleSlot` сохранить.

Следующий слот ищется по локальным датам, удовлетворяющим маске, с режимами `>= now` для включения/редактирования и `> now` для продвижения после due. Не прибавлять к UTC instant фиксированные 24 часа. При DST gap использовать существующее разрешение; если результат оказался на другой локальной дате из-за полного пропуска даты, пропустить такой кандидат. Поиск должен покрывать следующий повтор выбранного дня, включая пропуск целой даты; тесты охватывают переход недели и такой timezone edge case.

Обновить все пути `ScheduleSettingsOperations`: update, startup normalization и repair null cursor. Сохранять валидный due cursor для same-day recovery; исправлять курсор на невыбранную дату без отправки. В `DueUserRow` и SQL выборках загружать маску. В claim под существующим User lock:

1. Определить текущую локальную дату и её допустимый слот. Если день не выбран или время ещё не наступило, не создавать прошлый occurrence; продвинуть курсор к ближайшему будущему допустимому слоту.
2. Если сегодняшний слот наступил, резервировать его с прежним ключом `scheduled:<userId>:<local-date>` и immutable snapshots.
3. В той же транзакции установить следующий допустимый слот строго после `now`, в том числе если каталог пуст или occurrence уже существует, сохранив отсутствие бесконечного due-цикла.

Прежнее восстановление «latest overdue любого дня» намеренно сужается до сегодняшней даты для всех расписаний. Это явно изменённая часть time contract: иначе возобновление во вторник могло бы отправить пропущенный понедельничный вопрос вопреки выбранным дням. Пропущенные вопросы не накапливаются. Reclaim уже существующих claims не пересчитывает weekday и сохраняет прежние правила внешней доставки.

Альтернатива: фильтровать только due users по сегодняшнему weekday оставляет старый курсор и неверную дату occurrence. Одна проверка при отправке также недостаточна: календарный выбор должен происходить в транзакции claim.

### 3. Команды и короткий режим ввода времени

`/schedule` показывает сохранённое состояние, кнопки выбора дней, «Каждый день», «Занимаюсь сам» и кнопку изменения времени. `/time` показывает текущее время/часовой пояс, быстрые варианты 09:00, 13:00 и 18:00 и инструкцию отправить своё время в чат. Старые `set_time_H_M` остаются совместимыми быстрыми действиями; новые arbitrary значения не ограничены `TIME_OPTIONS`.

Открытие /time или кнопки времени из расписания создаёт в личном чате адресный ephemeral-контекст на 10 минут для конкретной пары chat id/sender id. В этот период ровно `ЧЧ:ММ` обрабатывается как новое время, с той же валидацией 00:00–23:59; успешное сохранение закрывает контекст, ошибки позволяют повторить ввод до истечения срока. Slash-команда или callback вне меню времени закрывает его без изменения расписания. Контекст хранится только в памяти процесса, не является conversation state, не записывается в БД и после рестарта исчезает. Голос всегда, а обычный текст вне контекста идут по существующей маршрутизации.

Дни выбираются в inline-клавиатуре как черновик: версия формата и компактная маска передаются в callback; только «Сохранить» вызывает сервис с patch `{ promptWeekdaysMask, dailyPromptEnabled: true }`. Отмена или незавершённый выбор не меняет БД. Пустой набор допускается в черновике, но не сохраняется. Повторное сохранение устанавливает те же значения. При нескольких открытых меню последнее успешно сохранённое действие определяет дни; старый черновик не несёт копий времени, timezone или настроек стрика и не может откатить их. Не требуется серверная wizard-сессия или новая таблица; ephemeral-контекст имеет только оперативный TTL 10 минут.

Callback `schedule_open` всегда читает актуального пользователя по `ctx.from.id`; идентификатор адресата рассылки в кнопке не передаётся. Все payload валидируются, callback acknowledgement и per-user sequencing используют существующий Telegram runtime. Неизвестная версия/невалидный callback предлагает открыть `/schedule` заново. После рестарта команда и неизменяющая кнопка продолжают работать.

Handlers остаются адаптерами: разбор команды/кнопки, вызов сервисов и формирование ответа. Допустима небольшая локальная декомпозиция нового schedule UI в TelegramModule; доменные вычисления остаются в ScheduleModule. В `setMyCommands` добавить `/schedule` и `/time`, уточнить описание `/settings`. Голос всегда и текст вне режима ввода продолжают существующую маршрутизацию.

Альтернатива постоянному wizard-состоянию или хранению черновика в БД создаёт лишний lifecycle. Короткий контекст с проверкой chat/sender, TTL и явной отменой покрывает ввод из рассылки и не перехватывает сообщения урока после истечения окна.

### 4. Показать выбор стрика после сохранения, без объединения двух настроек

После успешного сохранения неполной недели или ручного режима показать текущее `streakReminderEnabled` и абсолютные callback-действия включения/выключения, делегирующие существующему `StreakService.updateReminderEnabled`. Настройка дней не пишет streak-поля. При сохранении лишь времени в уже редком расписании также можно показать этот блок; открытие экрана само по себе не меняет настройки.

Текст блока:

> Расписание сохранено. Стрик сохраняется, если завершать разговор с ботом каждый день. В дни без вопроса можно начать разговор командой /start. Получение вопроса или незавершённый ответ не засчитывают день. Напоминания о стрике работают отдельно и могут приходить в дни без вопросов. Оставить их включёнными?

Последнюю фразу адаптировать к текущему состоянию; действия называются «Включить напоминания» и «Выключить напоминания», текущее значение отмечено. Блок не блокирует сохранённое расписание. Если второе сохранение не удалось, сообщить об ошибке выбора напоминаний, сохранив успешное расписание. Возвращение на семь дней не включает reminders неявно.

Альтернатива автоматического выключения не соответствует выбранному потоку отдельного решения пользователя. Привязка reminder eligibility к weekday изменила бы сохранённое ежедневное правило стрика и потому не применяется.

### 5. Независимые периоды в существующих фильтрах аудитории

Расширить `BroadcastFilters` optional полями `noVoiceForDays?: number | null` и `scheduledDeliveryWithinDays?: number | null`. Первое означает отсутствие принятых голосовых ответов N дней, второе — наличие хотя бы одной подтверждённой scheduled-доставки за M дней. Периоды независимы: каждый выключен при omission/null либо принимает JSON integer 1–365. Верхняя граница — явное ограничение формы и API; 14 не является default. Активные поля сохраняются в существующем `Broadcast.filters Json`, отключённые нормализуются к отсутствию.

Существующие `activity=any|7d|30d|90d|never`, `dailyPromptEnabled=any|true|false` и `languageLevels` сохраняются. Все заданные условия соединяются через AND; несовместимое пересечение даёт нулевую аудиторию, а не снятие фильтра. Новые фильтры не требуют включения вопросов: наличие доставки в прошлом и текущая настройка — разные условия. `mode` по-прежнему означает только `immediate|scheduled`.

Дополнить strict allowlist в `AdminBroadcastInputPipe`. Для body-периодов использовать проверку JSON number/integer/range, а не существующий query-helper `integer()`, принимающий строки. Неизвестные поля и некорректные значения возвращают 422; omission/null отключает только соответствующее условие. `normalizeBroadcastFilters`, preview/list/detail и audit snapshot должны сохранять все включённые поля. Повреждённое новое поле сохранённой конфигурации нельзя отбрасывать как отсутствующее: помечать конфигурацию ошибочной и блокировать dispatch, сохранив прежнее чтение legacy-строк без этих полей.

Предикат для момента T:

```text
status = active AND bannedAt IS NULL AND announcementEnabled = true
AND existing configured language/activity/dailyPromptEnabled predicates
AND when noVoiceForDays = N:
    (lastUserMessageAt IS NULL OR lastUserMessageAt < T - N * 24h)
AND when scheduledDeliveryWithinDays = M:
    EXISTS UserPrompt(
      userId = current user,
      source = scheduled,
      deliveryStatus = sent,
      sentAt >= T - M * 24h AND sentAt <= T
    )
```

`lastUserMessageAt` — durable факт принятой реплики; завершение урока и очистка transcript не меняют его смысл. `User.lastPromptSentAt` недостаточен для второго фильтра, поскольку объединяет manual и scheduled sends. Использовать `EXISTS`, не загружать историю в память; существующий индекс `(userId, deliveryStatus, sentAt)` — исходная опора запроса. Новый индекс нужен только при подтверждённой проблеме плана на тестовых данных.

Перед preview/create один раз захватывать T и передавать во все Prisma/SQL предикаты. Preview возвращает `evaluatedAt`; при create явно сохранять T как `Broadcast.createdAt`. Snapshot остаётся INSERT SELECT в транзакции с сохранением конфигурации, подсчётом и аудитом. Preview предварительный: при create число может измениться. Если оно стало нулём, сохранить существующее поведение пустой рассылки без отправок; UI не позволяет подтвердить заранее известный ноль.

При наличии хотя бы одного нового активного периода dispatcher перед каждой attempt повторяет весь настроенный предикат для конкретного snapshot user со свежим now. При отсутствии обоих периодов сохраняется прежняя проверка active/not-banned/announcementEnabled, даже если выбрана кнопка. Это сохраняет семантику старых рассылок; политика не привязывается к тексту или назначению сообщения. После проверки применяется прежний claim-token fence и фиксируется начало I/O. Не держать DB lock во время Telegram HTTP и не увеличивать snapshot.

Альтернативы: фиксированный сегмент не позволяет задавать разные периоды или использовать условия отдельно. Новая универсальная expression language с OR-группами не нужна для выбранного расширения: достаточно двух optional параметров рядом с прежними фильтрами.

### 6. Собственный текст и необязательное действие сообщения

Добавить `Broadcast.messageAction String? @db.VarChar(32)` с SQL CHECK `messageAction IS NULL OR messageAction IN ('open_schedule')`. Это самостоятельная настройка сообщения, не часть фильтров. В input DTO optional `messageAction` принимает null/omission либо `open_schedule`; в preview/list/detail сохраняется выбранное значение. Отдельная классификация рассылок не вводится.

В текущем scope форма предлагает «Без кнопки» и «Настроить расписание». Подпись и callback-data для поддерживаемого действия задаёт Telegram adapter; произвольные callback, URL, код команды или массив клавиатуры не принимаются от админки. Текст полностью вводит администратор; специальные тексты, шаблоны, пресеты и автоматическое заполнение формы отсутствуют. По умолчанию текст пуст, оба новых периода выключены, `messageAction=null`; существующие фильтры имеют прежние нейтральные defaults.

В `BroadcastSender.sendPlainText` добавить optional четвёртый аргумент options с выбранным действием, сохранив нынешний третий `AbortSignal`. `TelegramService` переводит `open_schedule` в inline-кнопку «Настроить расписание» / `schedule_open`; при null сообщение не имеет кнопки. Действие загружается вместе с filters/content в claim и воспроизводится после restart/retry. Не выводить его из текста, активности или значений N/M. Сохранённое неизвестное действие блокирует dispatch с ошибкой конфигурации, не деградируя молча до текста без кнопки. Неизвестные новые параметры не преобразуются в более широкую аудиторию.

Preview отображает точный нормализованный текст, выбранную кнопку либо её отсутствие, все включённые фильтры с периодами, evaluatedAt и число адресатов. Добавить N, M и messageAction в signature формы. Меняя действие или фильтры, UI не меняет введённый текст. Переиспользовать установленные shadcn-vue controls, loading/error/empty состояния и существующий AlertDialog, без обновления пакетов.

В списке и деталях показывать сохранённые условия и действие; настройки остаются видимыми после retention тела, а очищенный текст не восстанавливается. Дополнительные фильтры и кнопка доступны для любой рассылки независимо друг от друга. Комбинация N=14, M=14, enabled=true и open_schedule вводится вручную для исходной задачи; отдельного пункта меню или готовой конфигурации для неё нет.

Альтернатива хранению action в `filters` смешивает параметры сообщения и выбор аудитории. Nullable поле сохраняет независимость этих настроек без новой сущности кампании или enum её назначения.

### 7. Транзакции, совместимость и источники истины

Schedule edits сериализуются существующим User lock. Обновление маски/времени/enabled и курсора — одна транзакция, timezone transition продолжает использовать существующий streak callback. Не брать существующий UserPrompt lock после User lock: квалификация разговора сохраняет порядок UserPrompt → User. Новые поля не изменяют scheduled unique index и trigger immutable identity. Broadcast delivery использует существующие leases и terminal outcomes; не добавлять повтор unknown I/O.

Старые `toggle_daily`, `set_time_*`, настройки personality, анонсов и reminders остаются доступными. `AdminUsersService` сейчас меняет enabled через общий user patch; его сохранённый контракт on/off и repair нужно проверить с неполной маской, не добавляя новый admin weekday editor. Если для соблюдения null/future cursor требуется поправка, сделать её в существующей audited transaction, без изменения route/DTO. Не сбрасывать маску при административном on/off.

После реализации и проверки перенести только контракт расписания в основную `practice-scheduling` spec: заменить соответствующие пункты `docs/app.md` ссылкой в той же правке синхронизации. Общие timezone-правила для квот и стриков сохраняются в их прежних разделах. `streak-schedule-guidance` не заменяет полный streak contract. Обновить карту источников истины, архитектурные страницы Telegram/background jobs/admin и database contract; не переносить все анонсы или стрики в OpenSpec этим change.

## Risks / Trade-offs

- [Пользователь недавно зарегистрирован и ещё не успел ответить] → фильтр отсутствия голоса не имеет скрытого порога возраста аккаунта; администратор видит выбранные условия и число адресатов.
- [Preview и реальная отправка имеют разную аудиторию] → snapshot фиксируется при create, дальнейшие исключения отражаются в skipped, новые пользователи не добавляются.
- [Последний ответ принят между проверкой и Telegram I/O] → повторная проверка максимально близко к attempt marker; уже отправленный запрос не отзывается, как указано в spec.
- [Пользователь изменил расписание, когда вопрос уже claimed] → immutable claim может завершить доставку; экран подтверждает будущий слот, а тест сохраняет старую идентичность.
- [Снижение частоты не сохраняет ежедневную серию] → явный текст при сохранении и независимый выбор reminders, без скрытого изменения стрика.
- [Старый backend игнорирует маску, новые JSON-фильтры или действие] → запускать один актуальный runtime; не допускать overlap разных версий после включения новых функций. Rollback требует остановки фоновой работы и проверки активных записей.
- [Истечение ввода или рестарт] → снова открыть /time; команда с аргументом работает независимо от временного контекста.

## Migration Plan

1. Создать additive Prisma/SQL migration: `promptWeekdaysMask NOT NULL DEFAULT 127` с диапазонным CHECK и nullable `Broadcast.messageAction VARCHAR(32)` с CHECK поддерживаемого действия. Старые строки получают null action; `filters`, timestamps, получатели и streak history не переписываются. Новые периоды хранятся в прежнем JSON и не требуют собственных колонок.
2. Обновить generated Prisma client, runtime и admin types. Проверить upgrade fixtures с enabled/disabled users, нестандартными минутами и queued broadcasts без новых параметров. Новые user create/upsert получают mask 127.
3. Порядок внедрения: остановить старый runtime → применить миграцию → запустить новый backend → проверить preview с независимыми периодами и optional action на тестовых данных → опубликовать новую админку. Старый backend отклоняет новые body-поля с 422; новая форма открывается только после backend-проверки. Старый UI не отображает новые настройки, поэтому рассылки с ними создаются после обновления обеих частей. Startup normalization не отправляет вопросы.
4. Проверить настройки и preview на тестовых данных. Реальная рассылка создаётся только явным действием администратора; deployment не заполняет форму, не создаёт кампании и не отправляет сообщения.
5. При rollback остановить dispatcher/scheduler и новые записи. Проверить неполные маски, включая disabled: старый toggle впоследствии включит ежедневный режим. Проверить queued/processing broadcasts с новыми фильтрами или действием: старый dispatcher игнорирует их семантику. Ненулевые результаты блокируют запуск старого runtime. Предпочесть forward fix; преобразование пользовательских настроек или активных рассылок требует отдельного согласованного решения. Новые поля и данные сохраняются, destructive down-migration не входит в план. Уже разосланные кнопки расписания также требуют нового handler; даже нулевые DB counts не восстанавливают этот UX в старой версии.

Read-only проверки для rollback runbook, после остановки новых записей:

```sql
SELECT "dailyPromptEnabled", count(*) AS sparse_users
FROM "users"
WHERE "promptWeekdaysMask" <> 127
GROUP BY "dailyPromptEnabled";

SELECT "status", count(*) AS broadcasts_using_new_options
FROM "broadcasts"
WHERE "status" IN ('queued', 'processing')
  AND (
    "messageAction" IS NOT NULL
    OR "filters" ->> 'noVoiceForDays' IS NOT NULL
    OR "filters" ->> 'scheduledDeliveryWithinDays' IS NOT NULL
  )
GROUP BY "status";
```

Эти запросы ничего не исправляют автоматически. Runbook направляет оператора к forward fix или согласованной процедуре восстановления при ненулевых результатах.

Неразрешённых продуктовых вопросов нет. Предел периодов 1–365 дней и одна поддерживаемая кнопка — явные границы текущего расширения. Проверка планов SQL, имена локальных Telegram helpers и формулировки ошибок уточняются при реализации без изменения контракта.
